## 1. Вступ

Метою проєкту є розроблення серверного API для IoT-моніторингу, який дозволяє реєструвати пристрої, приймати від них телеметричні дані, зберігати ці дані у вигляді часових рядів, переглядати їх через REST API та створювати алерти на основі порогових значень.

Предметна область — моніторинг стану IoT-пристроїв і сенсорів. Типові дані: температура, вологість, рівень заряду, тиск, напруга або інші числові метрики.

Реалізовані функції:

- реєстрація користувачів;
- токен-автентифікація;
- керування IoT-пристроями;
- прийом телеметрії за ключем пристрою;
- зберігання часових рядів;
- фільтрація телеметрії;
- створення порогів алертів;
- автоматичне створення подій алертів;
- AI-аналіз телеметрії через фонову задачу Celery;
- Docker/Gunicorn/Nginx конфігурація.

## 2. Аналіз вимог

### Функціональні вимоги

1. Користувач може зареєструватися та отримати API-токен.
2. Користувач може створювати, переглядати, редагувати та видаляти власні пристрої.
3. Кожен пристрій має унікальний API-ключ для передачі телеметрії.
4. Пристрій може надсилати одну або декілька точок телеметрії.
5. Користувач може переглядати телеметрію власних пристроїв.
6. Користувач може створювати порогові правила для метрик.
7. Система автоматично створює алерт, якщо значення метрики виходить за межі порогу.
8. Користувач може переглядати, підтверджувати та закривати алерти.
9. Користувач може запустити AI-аналіз телеметрії за вибраний період.

### Нефункціональні вимоги

- MVT-структура Django;
- поділ на окремі Django apps;
- REST API на Django REST Framework;
- ORM для доступу до бази даних;
- міграції Django;
- змінні середовища для секретів і конфігурації;
- Docker-конфігурація;
- базові тести критичних сценаріїв.

### Ролі користувачів

**Звичайний користувач:**

- керує власними пристроями;
- переглядає власну телеметрію;
- створює власні пороги;
- переглядає власні алерти;
- запускає AI-аналіз власних даних.

**Адміністратор:**

- має доступ до Django Admin;
- може переглядати всі сутності;
- може адмініструвати користувачів і дані.

## 3. Архітектура застосунку

Проєкт побудований за архітектурними принципами Django MVT.

### Django apps

- `accounts` — реєстрація, профіль користувача, захищена dashboard-сторінка.
- `devices` — модель пристрою, API-ключі, CRUD пристроїв.
- `telemetry` — прийом і перегляд телеметричних точок.
- `alerts` — пороги та події алертів.
- `ai_agent` — генерація AI-висновків щодо телеметрії.
- `iot_monitoring` — конфігурація проєкту, загальні URL, Celery.

### Основні конфігураційні файли

- `settings.py` — конфігурація Django, REST Framework, SQLite, security flags, Celery, OpenAI.
- `urls.py` — маршрутизація на рівні проєкту.
- `docker-compose.yml` — служби web, celery, redis, nginx.
- `Dockerfile` — образ Django-застосунку.
- `.env.example` — приклад змінних середовища.
- `deploy/nginx.conf` — конфігурація reverse proxy та static/media.

## 4. Проєктування бази даних

У проєкті використано реляційну схему. База даних у цьому варіанті — SQLite. Це зроблено за окремою умовою роботи, хоча для production-середовища загальна вимога передбачає PostgreSQL/MySQL/MariaDB.

Основні таблиці:

- `Device` — IoT-пристрій користувача;
- `TelemetryPoint` — точка часового ряду;
- `AlertThreshold` — порогове правило;
- `Alert` — подія спрацювання порогу;
- `AIInsight` — результат AI-аналізу.

ER-діаграма наведена у файлі `docs/er_diagram.mmd`.

## 5. Реалізація ключових функцій

### Реєстрація користувача

Реалізована через `RegisterView`, `RegisterSerializer` та стандартну модель користувача Django. Після реєстрації створюється DRF token.

### Керування пристроями

`DeviceViewSet` дозволяє виконувати CRUD-операції над пристроями. Кожен пристрій належить конкретному користувачу. Доступ обмежено власником або адміністратором.

### Прийом телеметрії

`TelemetryIngestView` приймає POST-запит з заголовком `X-DEVICE-KEY`. Система перевіряє ключ пристрою, створює записи `TelemetryPoint`, оновлює `last_seen_at` пристрою та викликає перевірку порогів.

### Пороги алертів

`AlertThreshold` містить `min_value` та/або `max_value`. Якщо нова телеметрична точка порушує поріг, створюється `Alert`.

### AI-аналіз

`GenerateInsightView` створює об'єкт `AIInsight` і запускає Celery-задачу `generate_ai_insight`. Задача збирає статистику за період, формує prompt і викликає OpenAI API, якщо `OPENAI_API_KEY` налаштований.

## 6. Безпека

Реалізовані заходи:

- паролі зберігаються через стандартний механізм Django auth;
- автентифікація API через DRF token;
- доступ до даних обмежений власником;
- ORM використовується замість raw SQL;
- `SECRET_KEY`, `ALLOWED_HOSTS`, security flags і API-ключі винесені в `.env`;
- CSRF-захист активний для session-based views;
- production-ready прапорці `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` винесені в конфігурацію.

## 7. Інтеграція агента ШІ

Для AI-функції використано OpenAI API. Взаємодія винесена у фонову Celery-задачу. Користувач створює запит на аналітику, після чого задача обчислює агреговані метрики та генерує короткий операційний висновок.

Послідовність:

1. Користувач надсилає POST `/api/ai/insights/generate/`.
2. API створює `AIInsight` зі статусом `pending`.
3. Celery worker виконує `generate_ai_insight`.
4. Задача читає телеметрію, формує prompt, викликає OpenAI API.
5. Результат записується у `AIInsight.response`.
6. Користувач переглядає результат через GET `/api/ai/insights/{id}/`.

## 8. Розгортання

Проєкт містить `Dockerfile`, `docker-compose.yml` і `deploy/nginx.conf`.

Служби:

- `web` — Django + Gunicorn;
- `celery` — worker для фонових задач;
- `redis` — брокер Celery;
- `nginx` — reverse proxy і роздача static/media.

SQLite-файл зберігається у Docker volume `sqlite_data`.

Команди запуску:

```bash
cp .env.example .env
docker compose up --build
```

## 10. Висновки

У результаті реалізовано API для IoT-моніторингу з підтримкою пристроїв, телеметрії, часових рядів, порогових алертів і AI-аналітики. Основна складність полягала у коректному розмежуванні доступу між користувачами, організації прийому телеметрії без користувацької автентифікації та синхронізації цього процесу з алертами.

Подальший розвиток:

- перехід на PostgreSQL для production;
- WebSocket/SSE для live-оновлень;
- агрегації часових рядів;
- графіки для dashboard;
- розширена система notification channels;
- rate limiting для device ingest endpoint.
